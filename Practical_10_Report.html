1. Practical Objective & Problem Definition
Title: Asynchronous Processing with Event-Driven Architecture
Objective: To implement asynchronous background processing using Node.js native EventEmitter without external dependencies.
Problem Statement: Add a background notification system to the Task Management application using Node.js built-in EventEmitter. When a new task is created via the API (POST /tasks), emit a task:created event that is handled asynchronously to log a notification (task title, timestamp, assigned user). The main API response must return immediately without waiting for the event handler to complete. Demonstrate the difference between synchronous and asynchronous handling by logging timestamps at both the API response and event handler execution points.

In high-throughput microservices and REST backends, offloading ancillary responsibilities (such as sending confirmation emails, audit logging, webhook dispatching, or metrics aggregation) from the synchronous HTTP request-response lifecycle is crucial. Forcing clients to await external network I/O or background processing blocks the Node.js event loop and inflates round-trip latency. By utilizing the Observer Pattern implemented via Node.js native EventEmitter, the main controller commits the state change to MongoDB and responds immediately (sub-20ms), delegating subsequent notification actions to background event handlers.

3. Key Questions & Technical Analysis
Q1: What is Event-Driven Architecture (EDA) and how does Node.js EventEmitter implement the Observer Pattern?
Event-Driven Architecture (EDA) is a software design pattern where application flow is determined by the emission and consumption of distinct events.
  • The Observer Pattern: The EventEmitter class acts as the Subject, maintaining an internal registry of listener functions (Observers) mapped to specific event string keys (e.g., 'task:created').
  • Loose Coupling: The task creation controller only knows that a task was created; it has zero knowledge of whether that event triggers an SMS alert, an audit log write, or a webhook. Observers can be added, modified, or removed independently without altering core CRUD logic.
  • Zero External Dependencies: Because EventEmitter is built directly into Node.js (import { EventEmitter } from 'events'), it delivers high-performance in-process event handling without third-party npm packages.
Q2: Why must secondary operations (e.g., notifications, emails, analytics) be processed asynchronously outside the request-response cycle?
Coupling secondary operations to the main HTTP request creates severe architectural liabilities:
  • Latency Inflation: External operations (such as sending an SMTP email or calling a Slack webhook) take anywhere from 300ms to 3000ms. Forcing an end-user to wait several seconds for a simple task creation destroys user experience.
  • Fault Tolerance & Failure Isolation: If a third-party email server or notification API is down or times out, an inline synchronous handler causes the entire HTTP request to fail (500 error), even though the task was already persisted in the database. In an event-driven model, background worker retries can fail gracefully without failing the client's API call.
  • Resource Utilization: Shorter HTTP connection lifetimes free up server socket handles, connection pool slots, and memory buffers faster, allowing higher concurrent requests per second.
Q3: What happens to the Node.js Event Loop if a background handler executes CPU-bound synchronous code instead of asynchronous I/O?
Node.js utilizes a single-threaded event loop for JavaScript execution:
  • If an event listener executes asynchronous I/O (timers, file streams, network requests), Node.js offloads the operation to the operating system kernel or the internal Libuv thread pool, keeping the main thread free to handle incoming requests.
  • However, if an event listener performs a heavy synchronous computation (e.g., image resizing, intense cryptographic hashing, or an infinite loop), it blocks the event loop thread entirely. While that synchronous code runs, Node.js cannot process any other incoming HTTP requests, timer callbacks, or database responses.
  • Solution: CPU-bound tasks must be offloaded to worker_threads, Node.js Child Processes, or a separate worker microservice.
Q4: What are the trade-offs between in-process EventEmitter versus distributed message brokers (RabbitMQ / BullMQ / Kafka)?
While native EventEmitter is lightweight, zero-dependency, and ultra-fast for single-process architectures, enterprise systems scale using distributed message brokers:
  • Process Boundary Limitation: EventEmitter is restricted strictly to the current Node.js heap. In multi-instance / Kubernetes deployments, an event emitted on Instance A cannot be consumed by Instance B.
  • Durability & Crash Recovery: If the Node.js server crashes while an in-memory event callback is pending in the event loop, that notification is permanently lost. Distributed queues like RabbitMQ, Redis BullMQ, or Apache Kafka persist events to disk and support acknowledgments (ACK/NACK), automatic retries, dead-letter queues (DLQ), and horizontal worker scaling.
4. Implementation Code Structure

A) Native EventEmitter Notification Module (backend/events/taskEmitter.js):

import { EventEmitter } from 'events';

class TaskEventEmitter extends EventEmitter {}
const taskEmitter = new TaskEventEmitter();
const notificationLogs = [];

// Asynchronous background listener for task:created
taskEmitter.on('task:created', (payload) => {
  const handlerReceivedAt = new Date().toISOString();
  const startTime = process.hrtime.bigint();

  // Non-blocking background execution (simulated email/alert dispatch)
  setTimeout(() => {
    const handlerCompletedAt = new Date().toISOString();
    const durationMs = (Number(process.hrtime.bigint() - startTime) / 1e6).toFixed(2);

    notificationLogs.unshift({
      id: `notif_${Date.now()}`,
      event: 'task:created',
      taskTitle: payload.task?.title,
      assignedUser: payload.user?.name,
      timestamps: {
        apiEmittedAt: payload.emittedAt,
        handlerReceivedAt,
        handlerCompletedAt,
        asyncProcessingDuration: `${durationMs} ms`
      },
      status: 'DELIVERED'
    });
    console.log(`🔔 [ASYNC EVENT HANDLER] Notification logged for "${payload.task?.title}" (+${durationMs}ms)`);
  }, 300);
});

export default taskEmitter;

B) Task Controller with Event Dispatch & Timestamp Logging (backend/controllers/taskController.js):

export const createTask = async (req, res, next) => {
  const reqStartTime = process.hrtime.bigint();
  const apiEmittedAt = new Date().toISOString();

  const newTask = await Task.create({ ...req.body, user: req.user._id });
  invalidateTasksCache(); // Practical 9 Invalidation

  // Synchronous Blocking Mode Comparison (?sync=true)
  if (req.query.sync === 'true') {
    const syncResult = await processNotificationSync(newTask, req.user, apiEmittedAt);
    return res.status(201).json({
      success: true,
      executionMode: 'synchronous-blocking',
      timestamps: { requestReceivedAt: apiEmittedAt, blockingDelay: `${syncResult.durationMs} ms` }
    });
  }

  // Asynchronous Non-Blocking Mode: Emit event and respond IMMEDIATELY
  taskEmitter.emit('task:created', { task: newTask, user: req.user, emittedAt: apiEmittedAt });

  const durationMs = (Number(process.hrtime.bigint() - reqStartTime) / 1e6).toFixed(2);
  res.status(201).json({
    success: true,
    executionMode: 'asynchronous-non-blocking',
    timestamps: {
      apiEmittedAt: apiEmittedAt,
      apiResponseSentAt: new Date().toISOString(),
      totalApiDuration: `${durationMs} ms`
    }
  });
};
