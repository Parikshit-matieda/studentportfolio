1. Objective & Problem Statement
Title: Containerization with Docker and Docker Compose
Objective: To containerize the full-stack web application using Docker and orchestrate multiple dependent microservices using Docker Compose.
Problem Statement: Write production-grade Dockerfiles for both the React frontend and Node/Express backend of the Task Management application. Create a docker-compose.yml file that orchestrates the frontend, backend, and MongoDB containers together. The entire multi-tier application must run with a single docker-compose up command.

In modern cloud-native architectures, containerization eliminates the classic "it works on my machine" dilemma by encapsulating applications, their runtime dependencies, configurations, and system binaries into portable, isolated OCI images. Docker Compose provides declarative multi-container orchestration, allowing complex topologies comprising web frontends, REST backends, and database engines to be provisioned, networked, and managed through unified infrastructure-as-code manifests.

3. Key Questions & Technical Analysis
Q1: Why are Multi-Stage Docker builds beneficial for frontend applications like React, and what is the difference in final image size?
A single-stage build includes the entire Node.js runtime, npm package cache, build compilers, and full node_modules directory in the final production container, creating bloated images of 1.1 GB to 1.4 GB.
  • Multi-Stage Build Mechanics:
    1. Stage 1 (Builder): Uses node:20-alpine to install dependencies and execute npm run build, producing the compiled static assets in /app/dist.
    2. Stage 2 (Runner): Uses an ultra-lightweight nginx:alpine base. It copies only the compiled HTML/CSS/JS from Stage 1 into /usr/share/nginx/html, completely discarding Node.js, source code, and developer tools.
  • Result: Image size shrinks from ~1,100 MB down to ~25 MB (a 97.7% reduction!). This dramatically accelerates CI/CD deployment speeds, slashes network transfer overhead, and reduces the attack surface by eliminating unnecessary binaries.
Q2: How does Docker Compose provide automatic service discovery and internal DNS resolution between containers?
When services are attached to a user-defined bridge network (e.g., app-network):
  • Docker Engine embeds an internal DNS server at 127.0.0.11 inside every container.
  • Containers can resolve other containers by their service name (e.g., mongo, backend, frontend).
  • Consequently, the backend connects to MongoDB using mongodb://mongo:27017/studentportfolio without needing to know dynamic container IP addresses or relying on brittle hardcoded host IP configurations.
Q3: What happens to MongoDB data when a container is stopped or destroyed, and how do Docker Named Volumes prevent data loss?
Containers are inherently ephemeral. Any file written to the container's writable storage layer exists only as long as the container exists. If a container is stopped or deleted via docker compose down, all database collections stored inside the container would be permanently wiped out.
  • Named Volume Solution: By mapping mongo-data:/data/db, MongoDB's storage directory is mounted onto a managed storage location on the Docker host machine.
  • Persistence Guarantee: Even if the MongoDB container is destroyed, updated, or re-created, the named volume retains all database records, indexes, and users intact. Re-launching with docker compose up immediately reattaches the existing volume with zero data loss.
Q4: What is the difference between Dockerfile vs. Docker Compose in real-world application deployments?
  • Dockerfile: Defines the blueprint and build instructions for a single image (e.g., how to build the backend image). It operates at the single-component level.
  • Docker Compose: An orchestration tool that defines how multiple interrelated containers run together (networking, environment variables, startup order, volume mounts, port mappings, health checks). Instead of typing three complex docker run commands with manual network flags, docker compose up brings up the entire full-stack system with one single command.
4. Implementation Code Listings

A) Multi-Stage Frontend Dockerfile (Dockerfile):

# Stage 1: Build React Vite Application
FROM node:20-alpine AS build-stage
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

# Stage 2: Serve optimized static assets with Nginx Alpine
FROM nginx:alpine AS production-stage
WORKDIR /usr/share/nginx/html
RUN rm -rf ./*
COPY --from=build-stage /app/dist .
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

B) Production Backend Dockerfile (backend/Dockerfile):

FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm install --omit=dev
COPY backend/ ./backend/
EXPOSE 5000
HEALTHCHECK --interval=20s --timeout=5s --start-period=15s --retries=3 \
  CMD wget -q --spider http://localhost:5000/cache/stats || exit 1
CMD ["node", "backend/server.js"]

C) Multi-Container Compose Manifest (docker-compose.yml):

services:
  mongo:
    image: mongo:7.0
    container_name: task_mongodb
    ports: ["27018:27017"]
    volumes: [mongo-data:/data/db]
    networks: [app-network]
    healthcheck:
      test: ["CMD", "mongosh", "--eval", "db.adminCommand('ping')"]

  backend:
    build: { context: ., dockerfile: backend/Dockerfile }
    container_name: task_backend
    ports: ["5000:5000"]
    environment:
      - PORT=5000
      - MONGO_URI=mongodb://mongo:27017/studentportfolio
      - JWT_SECRET=charusat_itue301_practical11_jwt_secret_key_2026
    depends_on:
      mongo: { condition: service_healthy }
    networks: [app-network]

  frontend:
    build: { context: ., dockerfile: Dockerfile }
    container_name: task_frontend
    ports: ["80:80", "3000:80"]
    depends_on: [backend]
    networks: [app-network]

volumes:
  mongo-data: { name: studentportfolio_mongo_data }

networks:
  app-network: { name: studentportfolio_network, driver: bridge }
